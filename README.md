# SDE 작업현황 보드 (ITSM To-Do 미러)

현업이 ITSM에 등록한 요청을 미러링해, **SME·SDE 리더**가 할당 단계와 작업 현황을 대시보드로 확인하는 시스템.
읽기 전용 미러 + 2단계 할당(SME→리더→SDE) 워크플로우.

- **frontend/** — React + Vite (대시보드 UI) · Node 20 컨테이너
- **backend/** — Java Spring Boot (ITSM 어댑터·동기화·REST API) · JDK 21 + Maven 컨테이너
- **docker-compose.yml** — MariaDB + backend + frontend 3개 서비스

> 설계 배경·의사결정은 Obsidian `ITSM_SDE-note` vault 참고.

---

## 사전 준비 — Docker 만 있으면 됩니다
- **Docker + Docker Compose** (Docker Desktop 등)
- 로컬에 **JDK/Maven/Node 설치 불필요** — 버전을 컨테이너 이미지로 고정해서 씁니다.
  - Java: `eclipse-temurin-21` (JDK 21)
  - Maven: `maven:3.9`
  - Node: `node:20-alpine`
  - MariaDB: `mariadb:11.4`

## 실행 (한 번에 전부)
```bash
docker compose up
# (백그라운드로: docker compose up -d)
```
- 첫 기동은 이미지 pull + Maven 의존성 다운로드로 몇 분 걸립니다(캐시되어 이후 빠름).
- 접속: **http://localhost:5173** (대시보드) · http://localhost:8080 (API)
- **첫 사용자는 회원가입**부터: ITSM 계정 + 비밀번호로 계정을 검증하고, 역할(SME/SDE 리더)과
  소속(SME=법인, 리더=팀)을 등록한다. 이후에는 **ITSM 계정으로 로그인**한다.
- **샘플/시드 데이터는 없다.** 기본 `ITSM_MOCK=false` — 기동 10초 후부터 실제 ITSM To-Do API를 폴링해
  미러링한 데이터만 표시된다. (`ITSM_MOCK=true` 로 두면 폴링을 하지 않아 빈 대시보드)

### DB 스키마 / 초기화
- 스키마 원본은 **`backend/src/main/resources/db/schema.sql`** (Obsidian 노트 `10_DB스키마` 기준).
  `spring.jpa.hibernate.ddl-auto=none` 이라 엔티티가 테이블을 임의로 바꾸지 않는다.
- 전체 재생성(모든 데이터 삭제):
  ```bash
  docker compose stop backend
  docker exec -i sdeboard-mariadb mariadb -usdeboard -psdeboard sdeboard \
    < backend/src/main/resources/db/schema.sql
  docker compose up -d backend
  ```
  또는 backend 를 `DB_INIT=always` 환경변수로 한 번 기동(기동 시 DROP→CREATE).

## 인증 — 사용자별 ITSM 계정 (서비스 계정 없음)
로그인은 **각자의 ITSM 계정**으로 한다. 서비스 계정(`ITSM_SVC_ID/PW`)은 더 이상 쓰지 않는다.

| 항목 | 동작 |
|---|---|
| 회원가입 | ITSM 로그인으로 계정을 **검증**한 뒤 저장. 법인코드는 토큰(compCd)에서 자동 취득 |
| 로그인 | ITSM 인증 성공 = 로그인. `sessionId` 발급(클라이언트는 `X-Session` 헤더로 전송) |
| **비밀번호** | **저장하지 않는다.** DB에 컬럼조차 없다. 서버 메모리 세션에서만 보관 |
| 수집 범위 | **로그인한 사람의 세션이 살아있는 동안**만 그 사람의 To-Do 를 5분 주기로 폴링 |
| 밤사이 수집 | 없음(의도된 동작). 재기동하면 세션이 사라져 폴링도 멈춘다 |
| 조회 범위 | 내 것 + 같은 소속(SME=법인, 리더=팀) **가입자**들의 미러 합집합 |

> ⚠️ **계정 잠금 방지** — ITSM 인증 실패 시 재시도하지 않고 그 사용자의 폴링을 즉시 중단한다.
> 화면에는 "ITSM 재인증 필요"가 뜨고, 다시 로그인해야 재개된다.

```yaml
    environment:
      ITSM_MOCK: "false"
      # 운영(공인망): https://pulmuone-itsm.metanet.co.kr/api/externalapi
      # 개발(사내망): https://itsm-dev.gdc.metanet.co.kr/api/externalapi
      ITSM_BASE_URL: https://pulmuone-itsm.metanet.co.kr/api/externalapi
      ITSM_ORIGIN: https://pulmuone-itsm.metanet.co.kr
      # 세션 정책: false 로 두면 accessToken(30분) 만료 후 재로그인을 요구한다
      ITSM_KEEP_CREDENTIAL: "true"
```
이후 `docker compose up -d backend` 로 재기동.
- `itsm.mock=false`가 되면 동기화 스케줄러가 ITSM To-Do API를 주기 폴링해 미러링한다.
- ITSM 응답 필드명이 문서와 다르면 **`adapter/itsm/ItsmResponseMapper.java` 한 곳만** 수정.
- 새 ITSM 상태가 나오면 `application.yml` 의 **`itsm.flow`** 에 한 줄 추가 (아래 참조).

### 상태 흐름 (`itsm.flow`) — 진행률의 유일한 출처
운영에서 확인된 변경 요청의 진행 순서다. **진행률은 오직 이 순번에서 계산한다.**

| seq | staCd | 상태명 | 버킷 | 진행률 |
|---|---|---|---|---|
| 1 | 00566 | 변경접수 | NEW | 5% |
| 2 | | 공정할당요청 | NEW | 15% |
| 3 | 00622 | 공정처리 | DEV | 40% |
| 4 | | 구현완료 | DEV | 60% |
| 5 | | 통합테스트 | TEST | 72% |
| 6 | **00581** | **대기** | DEP | 78% |
| 7 | | 배포요청승인 | DEP | 84% |
| 8 | 00584 | 배포접수 및 준비 | DEP | 88% |
| 9 | | 배포승인 | DEP | 92% |
| 10 | | **배포완료** | DEP | 96% |
| 11 | 00635 | 변경완료확인 | DONE | 100% |

> 예전에는 진행률을 버킷(NEW/DEV/…)에서 뽑았다. 그래서 **"구현완료"가 상태명의 '완료' 때문에
> DONE(100%)으로 튀고, 다음 단계인 "배포요청승인"에서 DEP(90%)로 역행**했다.
> 이제 순번이 진행률을 정하므로 역행이 구조적으로 불가능하다 (`ItsmFlowTest` 가 이를 고정한다).
> `staCd` 는 확인된 것만 적으면 되고, 나머지는 상태명으로 매칭한다(공백 무시).
> `itsm.status-map` 은 상태코드로 버킷을 못박아야 할 때만 쓰는 override 다.
>
> **통합테스트(seq 5)** 는 ITSM 이 실제로는 건너뛰는 경우가 있다. 상세 화면의 '진행 단계' 는
> 관측 이력과 대조해 그런 단계를 **'ITSM 건너뜀'** 으로 구분해 보여준다.

**2026-09-08 — 9단계에서 11단계로.** `대기`(00581)·`배포완료` 는 **같은 요청 한 건의 이력에서 실측**됐다
(CSD260907000046: 변경접수 → 공정할당요청 → 공정처리 → 구현완료 → **대기** → 배포요청 승인 →
배포접수 및 준비 → 배포승인 → **배포완료** → 변경완료확인). CI 차이가 아니라 등록된 9단계에 빠져 있던 것이다.
- `배포완료` 는 flow 에 없으면 상태명 키워드로 DEP(90%)가 되어 **배포승인(95%) 뒤에서 진행률이 역행**했다 — 그 구멍이 막혔다.
- `대기` 의 뜻은 배포요청승인 직전이라는 위치로만 추정했다(bucket DEP). 확정되면 bucket 을 고칠 것.
- ⚠️ **CI별 공정 확장 목록은 여전히 대기 중**이다. 갈래가 여럿이면 순번 하나로는 부족하다.

### 완료된 건은 사라지지 않는다
ITSM 에서 '변경완료 확인' 을 누르면 그 건은 **To-Do 목록에서 빠진다**. 예전에는 그 순간
`request_owner.active=0` 이 되면서 화면에서도 통째로 사라졌다(DB엔 `work_status=DONE` 으로 멀쩡히 남은 채).
지금은 소유 매핑만 비활성화하고 **조회 범위에는 계속 둔다** — 목록에 `ITSM 할 일 종료` 배지와 내려간 시각이 붙고,
`할 일 종료` 필터로 따로 볼 수 있다. 마지막 소유자까지 내려간 시점에는 상태 이력에도 한 줄 남는다.

### 담당 배정 표시
목록 API 에는 "SME→리더→SDE" 를 구분하는 필드가 없다. 대신 **상태 순번**으로 본다 —
`itsm.assign-from-seq`(기본 2 = 공정할당요청) 이상이면 할당이 시작된 것으로 보고,
담당자 이름(`trfPerId`)이 실려 오면 **할당 완료 + 담당자 배정**으로 표시한다.

### 확인된 목록 API 응답 필드 (2026-09-08, 운영)
`data.content[]`: `reqNo` `reqTitle` `perNm` `reqTypCd/reqTypNm` `reqDt`(epoch ms) `defDueDate`(epoch ms)
`trfPerId`(담당자 **이름**) `staCd/staNm` `reqCompNm` `reqCatNm` `workNo` — 페이징은 `totalPages`/`last`.
> 목록엔 **요청 원문(body)·담당자 ID·담당 리더 필드·첨부 정보가 없다.** 상세 API 확인 후 보강 대상.
> 확인된 상태코드: `00566` 변경접수 · `00581` 대기 · `00584` 배포접수 및 준비 ·
> `00622` 공정처리 · `00635` 변경완료확인.

### 목록 화면
**대시보드와 요청 목록은 같은 표(`RequestTable`)를 쓴다** — 컬럼이 어긋나지 않는다.
`법인 · 요청번호 · 요청제목 · 요청자 · 담당자 · 진행 현황 · [보기]`
**상세는 오직 [보기] 버튼으로 연다 — 행 클릭은 동작하지 않는다.**
표의 모든 칸이 드래그 복사 대상이라(요청번호·제목을 복사해 쓰는 일이 잦다), 행 클릭을 살려 두면
"지금 텍스트를 선택 중인가"를 매번 추측해야 했다. 여는 방법을 하나로 고정했다.
상단 검색창은 법인·요청번호·제목·요청자·담당자·상태를 함께 훑는다.

**상세는 [보기] 버튼으로만 연다.** 행 클릭을 없앴으므로 이 버튼이 유일한 경로다 —
그래서 작고 흐린 보조 버튼이 아니라 **눈에 띄는 주 버튼**이고, 행 높이가 제각각이라 그 칸만 세로 가운데 정렬한다.

### 대시보드 목록은 요청 목록과 다르게 추린다
- **완료된 건은 표에서 뺀다.** 매일 보는 화면에서 끝난 일이 자리를 차지하면 처리할 건이 아래로 밀린다.
  건수는 위 **KPI '완료' 카드**에 그대로 남고, 머리에 `완료 n건 숨김` 이라고 적는다.
  전체는 **요청 목록**, 완료만은 **완료 목록** 에서 본다.
- 남은 건은 **신규 유입 / 진행 중** 두 묶음이다. 기준은 ITSM 등록일(`reqDt`)이 아니라
  **우리 시스템에 처음 나타난 시각**(`request_owner.first_seen` 중 가장 이른 값)이다 —
  화면이 답할 질문은 "언제 접수됐나" 가 아니라 **"내가 아직 못 본 건인가"** 이기 때문이다.
  뒤늦게 미러링한 건이 처음부터 '오래된 건'이 되어 버리는 것도 막는다.
- 경계는 `app.new-request-hours`(기본 **24**). 주말을 건너뛰려면 72 정도로 올린다.

상태별 조회는 **목록 카드 우측 상단의 커스텀 셀렉트**다(기본값 `전체`).
예전의 칩 나열을 대체한 것으로, 상태가 늘어나도 헤더 한 줄이 넘치지 않는다.

### 엑셀(XLSX) 내보내기
`GET /api/requests/export?filter=&q=` — **화면에서 보고 있는 그대로**(현재 상태 필터 + 검색어)를 서버가 만든다.
조회 범위 검사는 목록 API와 같은 경로(`DashboardService.list`)를 그대로 타므로 권한이 새지 않는다.

- 컬럼: `법인 · 요청번호 · 요청제목 · 요청자 · 담당자 · 상태 · 진행률 · 등록일 · 기한 · 할 일 상태`
- **상태가 `미할당`일 때만 `우선순위` 빈 열이 붙는다.** 현업이 채워 돌려주는 게 이 기능의 목적이라,
  다른 범위에서는 빈 열이 노이즈가 된다 (`ExportServiceTest` 가 고정).
- 요청번호는 **문자열 셀**이다 — 엑셀이 숫자로 바꿔 지수 표기로 깨지면 공유 문서로 못 쓴다.
- 첫 줄에 **"가입 N명 중 M명 연동 기준"** 을 박는다. 내보낸 파일은 부분 데이터이고,
  엑셀만 받아 본 사람은 그걸 알 방법이 없다.
- 파일명 `요청목록_{범위}_{YYYYMMDD}.xlsx` (한글 파일명은 RFC 5987 로 내려간다).
- 세션은 헤더로만 보내므로 `<a href>` 가 아니라 **fetch → blob** 으로 받는다(쿼리스트링에 세션 노출 금지).

### 작업 완료 목록 (`/api/requests/done?from=&to=`)
주간보고용 화면이다. 사이드바 **완료 목록** — 기간 프리셋(이번 주 / 지난 주 / 이번 달 / 전체) + 직접 지정,
법인별·담당자별 건수 한 줄, 그리고 **엑셀 내보내기**(`filter=COMPLETED`, `완료일(관측)` 열이 붙는다).

> ⚠️ **완료일은 ITSM 원본이 아니다.** 목록 API 응답에 완료일 필드가 없어서, `itsm_request.done_at` 에
> **이 보드가 완료를 처음 관측한 시각**을 넣는다. 폴링 주기(5분)와 **그때 담당자 세션이 살아 있었는지**에
> 좌우된다 — 금요일 저녁에 완료된 건을 월요일 로그인 때 처음 보면 월요일로 기록된다.
> 화면 맨 위와 엑셀 첫 줄이 이 사실을 그대로 밝힌다(접거나 숨기지 않는다).

`done_at` 이 채워지는 경로는 셋이다:
1. 폴링 중 상태가 **DONE 으로 바뀐 걸 본 순간** (가장 정확)
2. 완료 전이를 못 보고 **To-Do 에서 내려간 순간** (폴링 사이에 완료된 경우)
3. 기동 시 백필 — 위 둘을 놓친 기존 건을 `request_status_history` 에서 소급

**완료 상태(DONE)인 건에만 붙인다.** 반려·취소로 To-Do 에서 내려간 건에 완료 시각을 붙이면
주간보고 건수가 조용히 부풀어 오르고, 화면에서는 알아챌 방법이 없다 (`DoneListTest` 가 고정).
기간 경계는 **양쪽 다 포함**한다(월 00:00 ~ 일 23:59:59).

### 조회 범위 — 역할별로 기준이 다르다
| 역할 | 기준 |
|---|---|
| **SME** | **요청의 법인**(`req_comp_nm`)이 내 법인이면 **누가 미러링했든** 보인다 (+ 예전 소유자 기준 집합의 합집합) |
| SDE 리더 | 같은 팀 전체(리더 + 팀원 SDE)가 미러링한 건 |
| SDE | 자기에게 할당된 건만 |

SME 를 소유자 기준으로 두면, **도입 전에 이미 SDE 에게 넘어가 지금도 그 사람 To-Do 에 살아 있는 건**이
SME 화면에 끝내 나타나지 않는다. 그래서 2026-09-08 에 법인 기준으로 바꿨다.

- ⚠️ **인력풀 배정(1~5차)을 범위 기준으로 쓰지 않는다.** SDE 는 여러 법인을 담당하므로 그 사람의 To-Do 를
  통째로 넣으면 **다른 법인 요청이 섞여 들어온다.** 인력풀은 **표시**(담당자 옆 `2차` 배지)에만 쓴다.
- ⚠️ **법인 매칭은 문자열이고 공백을 무시한다.** ITSM 이 법인코드를 주지 않아(`compCd` 없음, `comp_cd` 전 건 NULL)
  가입 때 손으로 적은 값과 비교할 수밖에 없다. 표기 하나로 **조용히 0건**이 되는 걸 막으려고
  가입 화면 후보를 **관측된 `reqCompNm` 에서** 뽑고, 비교는 공백을 지우고 한다.
- **여전히 남는 한계**: 요청이 우리 DB 에 들어오려면 **담당자 중 한 명은 가입·로그인**해 있어야 한다.
  아무도 연동돼 있지 않은 건은 애초에 미러링되지 않는다(한계 L1 의 잔여분).

#### `inTodo` 는 전체 소유자 기준이다
"아직 ITSM 할 일에 있나" 는 **그 요청의 모든 소유자**를 보고 판정한다(예전엔 조회 범위 멤버만 봤다).
그래서 **SDE 가 처리 중인 건이 SME 화면에서 '종료'로 보이던 문제**가 사라졌다.

내려간 건의 배지도 둘로 나눈다 — 뜻이 다르기 때문이다:
- **`ITSM 할 일 종료`** (완료) — `work_status = DONE`
- **`추적 중단`** (경고색) — 완료가 아닌데 아무의 할 일에도 없다. 담당자가 아직 가입하지 않았을 수 있다

#### 상단바 '동기화 hh:mm:ss' 는 **서버가 ITSM 을 읽은 시각**이다 (2026-09-10 수정)
예전에는 `clockText()` — **브라우저 시계**였다. 화면을 연 시각과 [동기화] 버튼을 누른 시각에만 찍혀서,
서버가 5분마다 폴링해도 **가만히 두면 값이 영원히 안 바뀌었다**(사용자 지적). 실패했을 때조차
시각만 새로 찍혀 방금 된 것처럼 보였다.

지금은 `me.lastSyncAt`(서버 세션의 실제 동기화 시각) 하나만 보여준다.

- 브라우저는 **1분마다 `/api/auth/me`** 를 다시 읽는다(푸시가 없어 이것이 유일한 통로다).
  그래서 화면의 시각은 실제 동기화보다 **최대 1분 늦게** 따라온다.
- `lastSyncAt` 이 **실제로 바뀐 경우에만** 판(dataVersion)을 올려 열려 있는 화면이 다시 읽는다.
  1분마다 목록을 통째로 다시 읽지 않는 이유는 하나 — 바뀐 게 없으면 다시 그릴 이유가 없고,
  보고 있는 사람의 스크롤과 열어 둔 드롭다운만 흔들린다.
- ⚠️ 이 폴링의 401 을 삼키지 않는다. 세션이 서버에서 사라졌는데 조용히 넘어가면
  **시각이 멈춘 채 로그인 화면으로도 못 간다** — 사용자에게는 "동기화가 안 된다" 로만 보인다.
- ⚠️ 실제 폴링 간격은 **5~6분**이다. 서버가 1분마다 깨어나 "마지막 동기화 + 5분 지났나" 를 보므로
  300~360초 사이에서 흔들린다(`SyncService.scheduled`, `itsm.poll.interval-ms`).
- ⚠️ **세션이 있는 사람만 폴링한다.** 백엔드를 재기동하면 세션이 전부 사라지고
  **각자 다시 로그인할 때까지 폴링이 멈춘다**(in-memory `SessionRegistry`).

### SDE 회원가입 · 인력풀 (`/api/sde/pool`)
2026-09-08 — [[00_설계_개요]] §0 의 "**SDE 행동 변화 0**" 원칙을 **완화**했다(사용자 결정).
새 문구는 "**SDE 는 가입·로그인까지만. ITSM 에서 일하는 방식은 그대로**" 다.
SDE 가 가입해 로그인하면 자기 To-Do 가 미러링되고, **리더의 조회 범위가 팀원 것까지 넓어진다**(한계 L1 완화).

**인력풀**은 지금 리더가 엑셀로 관리하던 "1~5차 담당자" 표를 그대로 옮긴 것이다.

| | 규칙 |
|---|---|
| 줄 | 법인마다 블록 하나 — **법인담당SDE**(칩 띠) + **시스템별 차수**(표), 2026-09-10 `UR-260910-1` |
| 차수 | **줄마다 1~5차**. `sde.tiers` 로 조정 — 차수가 늘면 이 값만 올린다 |
| 유지 주체 | **SDE 리더**. 리더만 편집하고, **자기 팀 SDE 만** 배정할 수 있다 |
| SME | 자기 법인의 차수별 담당자를 **읽기만** |
| SDE | **내가 배정된 법인**의 차수 전부 읽기(`UR-260909-5`). 가입 시에는 **팀만** 고르고 배정은 리더가 채운다 |

#### 법인담당SDE(명단) 와 시스템별 차수(표) — 2026-09-10
사용자 요구는 두 단계로 왔다. ① *"차수가 시스템별로 설정되어야 한다"* ② *"법인의 담당자는 차수가 없다.
5명만 등록된다는 보장도 없다"*. 그래서 법인 블록 안이 **성질이 다른 두 영역**으로 나뉜다.

| 영역 | 무엇 | 저장 |
|---|---|---|
| **법인담당SDE** | 이 법인을 맡는 SDE **명단** — 차수 없음, 인원 제한 없음 | `sde_assignment` 中 `system_nm IS NULL AND tier IS NULL` |
| **시스템별 차수** | 시스템마다 1~5차 담당자 | `sde_assignment` 中 `system_nm IS NOT NULL` · 줄은 `team_system` |

- **차수 배지(`n차`)는 시스템 배정에서 뽑는다.** 법인담당SDE 에 차수가 없으니 다른 출처가 없다.
  ⚠️ 한 사람이 한 법인에서 차수를 여러 개 가질 수 있고(FNC 인사 3차 · 하루 1차) ITSM 은 요청이
  어느 시스템 건인지 주지 않는다. **하나를 고르면 틀린 숫자를 조용히 보여주므로** 고르지 않고
  이어 붙인다 — `1·3차`. 그래서 `RequestView.assigneeTier` 는 숫자가 아니라 **문자열**이다.
- ⚠️ **시스템 배정이 하나도 없으면 배지도 없다.** 정의대로다(차수가 어디에도 없는 상태).
- **법인↔시스템 귀속표는 우리가 만들지 않는다.** 어느 법인에 어느 시스템이 있는지는 아직 아무도 모른다 —
  `sde.systems` 는 **후보 18종**일 뿐이고, 짝은 리더가 화면에서 한 줄씩 만든다.
- ⚠️ **2026-09-10 이전에 저장된 법인 행은 `tier` 에 1~5 를 그대로 갖고 있다.** 화면도 배지도 그 값을
  쓰지 않는다(명단으로만 쓴다). 지우지 않은 것은 되돌릴 수 없어서다.

#### 담당자 선택은 드롭다운이 아니라 **검색 팝업**
칸을 누르면 화면 한가운데 목록이 뜨고, **이름·ITSM 계정·팀**으로 검색해 고른다(`MemberPicker`).
드롭다운은 여는 칸에 붙어 열려서, 표가 길어지면 **스크롤해야 보이는 사람이 생겼다**(사용자 2026-09-10).

- **`corp_nm` 이 코드가 아니라 문자열인 이유**: 목록 응답에 `compCd` 가 없다. 미러링한 사람의 토큰
  `compCd` 를 쓰면 *그 사람의* 법인이 박혀 틀린다. 그래서 ITSM 이 주는 `reqCompNm` 문자열에 맞추고,
  가입·배정 화면의 후보를 **관측값에서 뽑아** 오타로 조용히 어긋나는 것을 막는다.
- **"한 칸에 한 명" 은 DB 제약이 아니라 서비스에서 검사**한다 — 차수의 의미(순번 vs 업무 분담)가
  아직 확정되지 않아서다. 확정되면 `(corp_nm, system_nm, tier)` UNIQUE 로 올린다.
  `SdePoolServiceTest` 가 규칙을 고정한다.
- **줄을 내리려면 먼저 칸을 비워야 한다.** 법인 줄은 그 아래 **시스템 줄까지 없어야** 내려간다 —
  한 번에 (시스템 수 × 차수) 칸이 사라지는데 지우면 복구할 곳이 없다.

### 요청 분석 노트 (`/api/requests/{reqNo}/note`)
SME 가 현업 요청을 분석해 적는 **요구사항 정의서**. 할당받은 SDE 가 읽는다.
현업이 주는 것은 텍스트 몇 줄·PPT 몇 장이라 되묻는 과정이 반드시 생기는데, 그 왕복을 앞당기는 게 목적이다.

- **에디터는 리치 에디터(Quill)** 다. 마크다운을 쓰지 않는 이유는 하나 — **문법을 모르는 사용자가 많다**(사용자 결정).
- 상세 화면을 **드로어에서 페이지로 승격**했다. 왼쪽이 노트(주 작업물), 오른쪽이 ITSM 원본 정보다.
- 쓰기는 **그 요청 법인의 SME 만**. 리더·SDE 는 읽기만 한다. 목록에는 **`노트`** 배지가 붙는다.
- 낙관적 잠금 — 내가 열어 둔 사이에 다른 SME 가 저장했으면 **덮어쓰지 않고 409** 로 알린다.

> ⚠️ **`sde_assignment` 에 이어 두 번째로 이 보드가 원본을 갖는 데이터다.** ITSM 어디에도 없다.

#### 왜 HTML 이 아니라 Quill Delta(JSON) 를 저장하나
리치 에디터의 HTML 을 저장하면, 그리는 쪽에서 `dangerouslySetInnerHTML` 이 필요해지고
서버에는 HTML 새니타이저가 필요해진다. **그 자체가 주입 경로다** — SME 가 쓴 노트를 SDE 가 여는 순간이 공격 지점이 된다.

구조화 포맷만 오가면 그 경로가 없다:
- 저장: 서버가 들어온 ops 를 **다시 조립한다**(통과가 아니다). 모르는 서식·임베드·허용되지 않은 링크 스킴은 남지 않는다
- 표시: 읽기 전용 Quill 이 Delta 로 DOM 을 만든다 — 프런트 어디에도 `innerHTML` 로 본문을 넣는 곳이 없다
- 링크는 `http/https/mailto` 만 (대소문자 무시). `javascript:` 는 여기서 잘린다
- 상한 512KB. 검색·미리보기·내보내기용 **평문(`body_text`)** 을 서버가 함께 만들어 둔다
- `RequestNoteTest` 가 이 경계를 고정한다

> **Quill 은 `2.0.2` 로 고정**했다 — 2.0.3 에 HTML export 경로 XSS 권고(GHSA-v3m3-f69x-jf25)가 있다.
> 우리는 그 기능을 쓰지 않지만, 굳이 취약한 버전을 둘 이유가 없다. `npm audit` 0건.
> **이미지 첨부는 1단계에서 뺐다**(사용자 결정) — 붙이는 순간 파일 저장·용량·백업이 따라온다.

### 스키마 변경은 `SchemaMigration` 으로 (DROP 금지)
스키마는 `db/schema.sql` 로 관리하지만 그 파일은 `DB_INIT=always` 일 때만 실행되고, 그 모드는 **DROP → CREATE** 다.
컬럼 하나 늘리자고 미러를 비울 수는 없으므로, 운영 중인 DB 에는 `service/SchemaMigration` 이
**덧붙이기 전용 DDL**(`ADD COLUMN IF NOT EXISTS` 등)을 기동 시 1회 적용한다.
여기 넣는 문장은 **몇 번 실행해도 같은 결과**여야 하고, 컬럼 삭제·타입 변경처럼 되돌릴 수 없는 것은 넣지 않는다.

### 로그인 — 아이디 저장
로그인 화면의 **아이디 저장** 체크박스는 **ITSM 계정 ID만** `localStorage` 에 남긴다(`sde.loginId`).
⚠️ **비밀번호는 저장하지 않는다.** 서버조차 DB 에 남기지 않는 값이라(세션 메모리 전용),
브라우저에 두면 그 원칙이 여기서 무너진다. 로그아웃해도 아이디는 남는다 — 그게 이 기능의 목적이다.

## 원격 접속 (Tailscale 등) — "CORS로 막힌다" 할 때
증상의 실제 원인은 대부분 CORS가 아니라 **Vite의 Host 검사**다.
Vite 5.4.12+ 는 DNS 리바인딩 방어로 Host 헤더를 검사하는데, **IP는 기본 허용이지만 호스트명은 차단**한다.
MagicDNS 이름(`mymac.tailxxxx.ts.net`)으로 열면 다음이 뜨고, 브라우저에선 API 실패처럼 보인다.
```
Blocked request. This host ("mymac.tailxxxx.ts.net") is not allowed.
```

| 접속 주소 | 결과 |
|---|---|
| `http://100.x.x.x:5173` (Tailscale IP) | 정상 — IP는 기본 허용 |
| `http://mymac.tailxxxx.ts.net:5173` | `.ts.net` 을 기본 허용해 두어 정상 |
| 그 외 호스트명 | `VITE_ALLOWED_HOSTS` 에 추가 필요 |

```yaml
# docker-compose.yml · frontend
    environment:
      VITE_ALLOWED_HOSTS: ".ts.net,mypc.local"   # 또는 all (신뢰된 망에서만)
```

### API 요청 경로
프론트는 `/api/...` 상대경로로 호출하고 **Vite가 백엔드로 프록시**한다 → 브라우저 입장에선 같은 오리진이라
CORS가 발생하지 않는다. 굳이 백엔드(:8080)를 직접 호출해야 한다면 오리진 패턴을 열어둔다.
```yaml
# docker-compose.yml · backend
      APP_CORS_PATTERNS: "http://localhost:*,http://100.*:*,http://*.ts.net:*"
```
기본값에 `localhost / 127.0.0.1 / 100.* / 192.168.* / 10.* / *.ts.net` 이 이미 포함돼 있다.

> 더 깔끔한 대안: `tailscale serve --bg 5173` 로 HTTPS 단일 오리진(`https://mymac.tailxxxx.ts.net`)으로
> 노출하면 포트 개방 없이 접속된다. 이때도 위 `allowedHosts` 설정이 필요하다.

### (선택) 로컬에서 직접 실행하려면
Docker 없이 돌리려면 JDK 21 + Maven + Node 18+ 설치 후:

## ITSM API 확인 (Phase 0)
실제 응답 구조를 확인하는 전용 엔드포인트 — 사내망에서 사용:
```bash
curl -X POST http://localhost:8080/api/itsm/verify \
  -H "Content-Type: application/json" \
  -d '{"username":"ID","password":"PW",
       "endpoint":"/my-page/my-to-do-request-operation",
       "payload":{"direction":"DESC","pageNum":0,"itemPerPage":3,"usePaging":"Y","sortBy":"reqDt","searchCriteria":{}}}'
```
로그인 → 지정 엔드포인트 호출 → **ITSM 원시 JSON 그대로** 반환한다. 이 응답으로 미러 필드/첨부 유무를 확정한다.
